## 先把词说清

**这一节回答**：后面反复出现的十来个词，各是什么意思。读完这张表，剩下的内容不需要任何背景知识。

| 词 | 意思 |
|---|---|
| harness | agent 的外壳：负责跑循环、调工具、存历史、决定每一轮把什么发给模型，模型只负责想下一步做什么。sage 就是这样一个外壳，本文说的全部结构都在它里面。 |
| KV cache | 键值缓存。模型读一段内容时会算出一批中间结果并缓存下来；下一次只要开头那段逐字节没变，就能接着往后算。省钱也省时间。 |
| 前缀 | 发给模型的内容里，从头开始逐字节没变的那一段。缓存只对前缀有效——中间改一个字，后面全部作废。这条约束是后面所有设计的起点。 |
| Log | 只追加的历史：发生过什么就记什么，从不回头改写。harness-pi 里它叫 SessionStore，sage 从那里搬走 append-only 这套设计，实现在本仓重写。每条 entry 先写进 JSONL 文件再进内存，磁盘永远是内存的超集，没有持久化水位计数器。 |
| View（视图） | 这一轮真正发给模型的那份内容，由 Log 算出来。Log 是全部，视图是这一轮选中的那部分。 |
| 块（chunk） | 调度的最小单位：一次工具调用，加上它返回的结果。两条消息算一块，只能整进整出。 |
| 档位（tier） | 一块在视图里以什么形态出现，四选一：不展示 / 一行 / 摘要 / 全文。 |
| claim（申领单） | 插件递给编译器的一张单子：我是谁、要占多少、降到哪些档位还能用、能不能被降。本设计的新概念，harness-pi 里没有对应物。 |
| 阶段（epoch） | 前缀被逐字节冻结、一个字不动的一段时间。阶段内只往尾部追加；换一个阶段就意味着前缀重算一次。视图因此有两个速度：前缀慢，尾部快。 |
| 留桩（stub） | 一个块被省略之后，留在视图里的那一行短记号：它是什么、有多大、怎么把原文取回来。 |

## 一句话

**这一节回答**：这份设计主张什么。

> 今天所有 agent 都把「对话记录」当成 agent 的状态，所以只能往后追加、满了压缩、坏了重开。sage 从第一天就把**记录**和**发给模型的内容**分成两样东西，并且让后者由一个**会算账、会留痕的编译器**算出来——前缀按阶段冻结，只有尾部每一轮变。走到这一步，sage 就有了三样别的 harness 结构上做不到的东西——看得见每个 token 为什么在那里、在阶段边界零代价换模型、子任务和后台任务不复制历史。

**为什么这条路走得通。**两件事在 harness-pi 仓库里可以直接核对，它们是这个设计的经验来源：那边内核的消息数组只 push、从不 splice 或重排，注释把它写成不变量（持久化水位能成立，前提就是数组索引稳定）；而那边做压缩的三个插件全都只改「这一轮发给模型的那份内容」，不写落盘历史——原文始终留在 store 里。也就是说「记录与视图该分开」这件事已经被一个真跑着的 harness 用实践验证过了，剩下的问题只是「算视图的那段代码该长什么样」。sage 不必再走一遍先合后分的路，直接从分开的形态起步。

## 今天的问题长什么样

**这一节回答**：为什么值得重写？一个能跑的东西，坏在哪里。

下面说的「今天」指 harness-pi 里那条链，也是绝大多数 harness 的做法。

设想一次无人值守的 run，跑到第 37 轮，历史攒了 15 万 token。在把内容发给模型之前，内核先拿出自己手里那个消息数组，交给一条叫 `transformMessagesBeforeLlm` 的管子，挂在上面的插件一个接一个地改它：microcompact 把旧的、可以重新取得的工具输出换成占位符；autoCompaction 发现估算体积超过阈值，把前面的消息总结成一条；trimHistory 再按条数把更早的工具结果换成占位符。改完发出去，下一轮从头再来一遍。这条链每天都在正常工作，问题不在某一步做错了，而在两件事同时成立：

**谁先谁后只写在注释里。**microcompact 的文件头用一整段解释它为什么必须排在 autoCompaction 之前，还专门写了一句「别套用另一条规则来反推顺序」。这条铁律靠人读注释维持，装配器不检查。harness-pi 的生产级架构那份文档把它记成差距 G2，旁边还记着：做装配的那个函数已经 215 行，加一个能力要改四处。

**总结一次，缓存全丢，而且要不回来。**总结发生的那一轮，前缀从头换过，之前攒的缓存全部作废，下一轮全价重读一遍。那边的内核为此特意复用同一个 summary 对象，让总结之后的前缀重新稳定下来——说明缓存这笔账是有人算的，只是没人决定「什么时候该付」：它是被阈值逼出来的，不是被算出来的。而且摘要有损。模型问「刚才那个文件第 80 行是什么」，没人答得上；microcompact 的占位符说的是「可以重新调一次工具」，可重调不等于取回——文件可能已经被改过，bash 的输出也不可重现。

![今天与提案的对照：上行是内核持有数组、三个插件排队改它；下行是内核只留 Log 与 View seam 两个原语，视图由一个编译器插件每轮算出来，另有编译清单与 expand 两条旁路](./fig1-today-proposal.svg)

*图 1：上行是 harness-pi 里「发给模型之前」发生的事——内核手里的数组既是记录又是视图，三个插件排队改它，顺序只写在源码注释里（生产级架构文档把这条差距记成 G2）。下行是 sage：内核只留 Log 与 View seam 两个原语，视图由一个编译器插件每轮算出来，另有编译清单与 expand 两条旁路。*

两行最左端是同一个东西——这套方案不动落盘历史的形态，只换「算视图」的那一段。上行把三个插件并排画出是为了列全；harness-pi 的实际装配里 microcompact 与 trimHistory 一般二选一，microcompact 的文件头写明它是后者的升级版。

## 内核长什么样

**这一节回答**：一个以「极简内核」为卖点的东西，为什么反而更简？

内核不持有那个消息数组当作真相。它只留两个原语：

| 原语 | 内核负责什么 | 从 harness-pi 搬什么 |
|---|---|---|
| Log | 只追加、先落盘再进内存、血缘关系。发生过什么就记什么，从不回头改。 | 搬 `session-store.ts` 的 append-only 设计与并发契约，实现在本仓重写（不要 HWM 计数器；去掉 `compaction_boundary`，换成 `view_epoch`） |
| View seam | 每次调用模型之前调一次 `view(log, turnCtx)`，拿回这一轮的视图。内核只检查一件事：视图里的 toolCall 必须成对。 | 没有对应物。这是 sage 自己的那条接缝 |

这条接缝长什么样（示例，非现有代码）：

```ts
interface ViewProvider {
  view(log: SessionLog, turn: TurnContext): Promise<CompiledView>;
}

interface CompiledView {
  messages: Message[];   // 这一轮真正发出去的内容
  manifest: Manifest;    // 每一块为什么在、为什么不在
  epoch: number;         // 这一轮用的是哪个冻结前缀
}
```

### 然后这些东西本仓不做

把视图收成一个来源之后，harness-pi 内核里好几样东西在 sage 里就没有存在的必要。这不是重构口号，是一张能逐条对账的表：

| harness-pi 里的东西 | 它在那边干什么 | sage 里怎么办 | 为什么不搬 |
|---|---|---|---|
| `_messages[]` 当真相 | 内核持有的那个数组，既是落盘的记录，又是发给模型的底稿 | 不要 | 记录归 Log，视图归 seam。一个东西不再兼两个职 |
| `transformMessagesBeforeLlm` | 一个 hook 位，串着好几个插件轮流改同一个数组 | 不要，换成单一的视图提供者 | 顺序铁律不会出现，因为不再有顺序可排 |
| `compaction_boundary` 的内核特判 | 内核认识一种叫「压缩边界」的落盘条目，重放时丢弃它之前的前缀、改从摘要接上 | 不要，落盘条目换成 `view_epoch`，怎么用是视图插件内部的事 | 压缩边界只是阶段清单的一个特例：「它之前的全部 → 一条摘要」 |
| `getCacheSafeParams()` | 给子会话交出一份「缓存安全」的内容。为了名副其实，它得专门写一段代码，把内核内部那份投影再算一遍 | 不要，子会话直接拿「当前视图」 | 视图只有一个来源，就不会有第二份需要追平的投影。harness-pi 的裁决②点名过这处缺陷，那边已按裁决修好——修法没问题，但它修的是「两份投影要对齐」这个结构，sage 不制造这个结构 |
| 悬空的 toolCall | 一块被切掉一半就会留下没有结果的调用，严格的 provider 直接返 400，重试队列每次都撞在同一条坏历史上。harness-pi 的裁决⑤把它列为确定性资损路径 | seam 上一条断言：视图交出来的那一刻就查 | 那边是在重放那一层修的尾部配对，主路径不过这道检查。视图既然由插件算出来，就该在交出来的地方查一次。两件事互不替代，sage 只保留后者 |

**内核小，是因为只拥有对的原语。**对着 harness-pi 数：少了一个 hook 位、一处条目特判、一段追平投影的代码，多了一条接缝和一条断言。「极简核心」从来不是少做事，是只拥有对的原语——harness-pi 的内核多拥有了一个数组，代价是所有人都得排队改它。

## 一轮编译怎么走

**这一节回答**：第 37 轮到底发生了什么？这是全文最重要的一节——前面所有的概念在这里合成一次具体的动作。

编译器是一个插件，它在 View seam 上被调用一次，走六步。下面这张图里的数字都是示意，用来让步骤看得见；真实的数值要等它跑起来才有。

![一轮编译的六个步骤：收 claims、确定性淘汰、打分、阶段判定、组装、发出并留痕；每一步下面挂着这一轮的具体情形](./fig2-one-round.svg)

*图 2：第 37 轮的这一次编译——收 claims、确定性淘汰、打分、阶段判定、组装、发出并留痕。上排是步骤，下排小卡是这一步在这一轮具体看到了什么。数字为示意。*

图上没写下的三处细节。

**第 ② 步为什么排在打分之前**：它是纯规则，不用模型也不用估值——`read(a.ts)` 在第 12 轮和第 31 轮各发生过一次，后一次覆盖前一次，前一份直接作废；失败重试留下的中间输出同理。先扔掉这些，打分器要处理的块就少了一批，而且这一部分的结论永远可复现。

**第 ③ 步是唯一可以换件的地方**：默认打分器是一套确定性规则，换成一个便宜模型来打，只换这一个部件，前后都不受影响。

**第 ④ 步是唯一主动花钱的决定**：它必须算，不能凭阈值——账怎么算见下一节。

这一轮的编译清单（写进 session-log）· 示例格式，非现有实现：

```json
{
  "epoch": 3, "turn": 37, "budget": 42000,
  "claims": [
    { "id": "progress-ledger", "tier": "full", "reason": "pinned",            "tokens": 820 },
    { "id": "tool-catalog",    "tier": "line", "reason": "budget:downgraded", "tokens": 120 }
  ],
  "chunks": [
    { "id": "c0142", "tier": "none",    "reason": "scorer:0.12",         "tokens": 4100 },
    { "id": "c0151", "tier": "none",    "reason": "superseded_by:c0188", "tokens": 2600 },
    { "id": "c0163", "tier": "summary", "reason": "scorer:0.48",         "tokens": 310 }
  ]
}
```

清单里每一块都有一个 `reason`，这是整套设计里最便宜也最值钱的一条约束：**不允许有「不知道为什么在那里」的 token**。四个档位分别是：不展示 / 一行 / 摘要 / 全文。

模型这一轮看到的样子（四行示意）· 示例格式，非现有实现：

```text
[进度账本] 目标：给 leaseQueue 加退避 · 已定：指数退避、上限 30s · 待办：补单测
[#c0142 · bash · 4.1k tokens · 已省略 · expand("c0142") 可取回原文]
[#c0163 · read(a.ts) · 摘要：导出 leaseQueue 与四个内部函数，重试逻辑在 88–121 行]
… 最近 6 轮全文 …
```

留桩和占位符的区别在这里：占位符说的是「你可以重新调一次工具」，留桩说的是「原文还在，按这个编号来取」。文件可能已经被改过、bash 输出不可重现，所以这两句话不是一个意思。每一次 `expand` 被调用，都说明打分器上一轮判错了一次——这个比率可以在线统计，见「效率只认三个数」一节。

## 插件怎么跟编译器打交道

**这一节回答**：插件式的 harness，多了一个总调度之后，还剩多少插件式？

harness-pi 里插件往上下文里加东西走的是 `additionalContext`：每个插件各给一段文本，内核按注册顺序拼成一条消息挂在末尾。那边的文档专门论证过这里为什么是「各给一段再合并」而不是「一个接一个改」——插件之间不耦合、可以并行，这是对的，sage 保留这个方向。代价是**没有人算总账**：文档只能把「一次注入 50KB」写成反模式，靠插件作者自觉。

这不是假想的风险，harness-pi 里有三处现成的痕迹，每一处都写在插件自己的文件头里：

| 哪里 | 发生了什么 | 说明什么 |
|---|---|---|
| skills 的目录 | 技能目录挂在 system prompt 末尾、每轮都发，但做 token 估算的插件读到的是改写之前那份 system prompt，所以目录的字节不进估算 | 文件头把它写成已知限制——「体积小，影响可忽略」。可忽略的前提是只有一个人这么干 |
| 工具目录的估算 | deferredTools 把「这一轮真正列出来的工具」写进共享状态给压缩插件用，但内核固定先跑消息管子再跑工具管子，压缩插件读到的永远是上一轮那份 | 文件头写明这跟注册顺序无关，是结构性的一轮滞后，排序也消不掉 |
| 压缩后的文件重读 | 那个插件自带「最多几个文件」和「每个文件最多多少字节」两个上限，注释写着「避免把刚省下的 token 又灌回去」 | 一个插件不得不替全局算账，正是因为没有全局的账 |

### 换成 claim

sage 只改一件事：插件不提交文本，改成提交一张**申领单**——我是谁、我要占多少、降到哪些档位还能用、能不能被降。编译器在总预算下解一次分配，产出清单。

一张申领单（示例，非现有代码）：

```ts
ctx.claim({
  id: "tool-catalog",
  pinned: false,
  priority: 40,
  tiers: { none: 0, line: 120, summary: 900, full: 6200 },
});
```

**编译器只认 claim，不认文本。**没有申领单的文字进不了视图。这一条让「上下文里有什么」变成可以枚举的集合，而不是一堆插件的副作用之和。

**预算不够时，从低优先级、高档位开始降。**降档不是删除：一百行的工具目录降成一行，模型仍然知道有什么可用，只是不知道参数长什么样。钉住的那些永远不降。

**每个插件占了多少，清单上看得见。**谁多占了，不需要争论，翻这一轮的清单即可。

**「要不要自带电池」的争论到这里就没有了。**带一百个工具的目录只占一百行预算，多带的那部分自己降档；谁挤掉了谁，清单上写着。sage 一开始就走这条路的是这几处：system-reminder、skills 的目录、延迟暴露工具的工具目录、压缩后重读文件的那一份重读、以及下面要说的进度账本。

## 什么时候值得开新阶段

**这一节回答**：「主动放弃缓存、换一份更小的前缀」这个决定，凭什么下？

先看形状。同一段长会话，两种做法下「发给模型的上下文」是这样走的：

![示意图：同一段长会话里，发给模型的上下文 token 随轮次的变化。现状是一路上涨、撞到压缩阈值就骤降的锯齿；目标是阶段内前缀冻结、只在尾部追加的平缓上行，只在阶段边界小幅回落](./fig-session.svg)

*图 3：同一段长会话，两种做法下「发给模型的上下文」怎么走。曲线是手画的示意，不是任何一次真实 run 的数据。*

红线的每一个下降沿，都是一次「摘要有损 + 前缀整段换过 + 下一轮全价重读」，而且下不下降由阈值决定，跟这一刀划不划算无关。蓝线里前缀在一个阶段内逐字节不动，新内容只往尾部加，所以缓存持续命中；只有阶段边界才会回落，那一次回落是被一道成本不等式批准的。

### 先说清两个速度

缓存只认逐字节相同：前缀里改一个字，后面全部作废，没有「部分保留」这个中间态。所以视图被拆成两层，各按自己的速度变：

| 层 | 多久变一次 | 谁决定 | 能不能每轮挑「最有价值的」 |
|---|---|---|---|
| 前缀（冻结的视图） | 只在阶段边界重算 | 下面那道成本不等式 | 不能。阶段内它是死的，这正是缓存命中的来源 |
| 尾部 | 每一轮 | 编译器 | 能。新的申领单、新的块、留桩、expand 取回的原文都落在这里 |

这意味着「每一轮都是最有价值的上下文」要打一个折：每轮能优化的只有尾部；前缀是上一次阶段边界时认为最有价值的那份，之后就不动了，哪怕中途某一块已经没用。这是有意的取舍——为了缓存，接受前缀里暂时留着一些过时的东西，直到下一次重算把它们清掉。它主动放弃的是「永远不重建」的极致，换来的是可以在算得过账的时候花这笔钱；而重算又比阈值压缩干净得多：按块选档、有清单、原文可以取回，不是一刀切的有损摘要。

所以「阶段」就是前缀被冻结的那一段时间，「开新阶段」就是主动把它作废、换一份更小的。这是整套设计里唯一一个主动花钱的决定，因此它必须能算。判据只有一句话：**接下来要少读的，得比现在多写的多。**

### 不等式与口径

```text
(旧视图 − 新视图) × 读价 × 预计剩余轮数  ＞  新视图 × 写价 − 旧视图 × 读价 + 预计取回 × 写价
```

口径写在这里，省得回头对不上：

- 每轮节省 = (旧 − 新) × 读价
- 重建额外成本 = 新 × 写价 − 旧 × 读价 + 重建后代价——减掉的那一项是因为重建的那一轮本来也要付旧视图的读价，不能重复计
- 重建后代价 = 预计取回 × 写价。压缩不是白省：甩掉的块里总有一部分会被 `expand` 拿回来，拿回来的原文要再写进缓存。预计取回按本会话已观测到的 `expand` 次数与平均结果大小估，还没观测到时用具名先验（甩掉部分的一成），且不超过 旧 − 新
- 回本轮数 = 额外成本 ÷ 每轮节省，向上取整
- 额外成本不大于 0 就是立即回本
- 阶段承诺：按回本批准的重开，承诺新阶段至少活过它自己的回本轮数。承诺值就是阶段第一份清单里的回本轮数，从 Log 读；阶段还没活到承诺值时，下一次按回本的重开要等。立即回本和上下文窗口安全阀不受限——前者那一轮本身就更便宜，挡住它等于为沉没成本买单

两个倍率以「输入价 = 1」为基准，取自这次调用的定价（`request_header.pricing`），来源记在清单上。价格页写明「未命中按输入价、无创建费」的型号，目录里的写价就是输入价。只有定价缺失时才用 0.1 与 1.25。下面算例里的 0.1 与 1.25 就是这组默认值。

三组算例（默认值一行，两组变体；单位都是「输入价当量 token」）：

| 算例 | 旧视图 | 新视图 | 剩余轮数 | 读价 | 写价 | 每轮省下 | 重建多花 | 几轮回本 | 结论 |
|---|---|---|---|---|---|---|---|---|---|
| 默认值 | 150,000 | 40,000 | 20 | 0.1 | 1.25 | 11,000 | 35,000 | 4 | 值得（4 轮回本，还剩 20 轮） |
| 变体 A：甩得少、快收尾 | 150,000 | 120,000 | 5 | 0.1 | 1.25 | 3,000 | 135,000 | 45 | 不值得（45 轮才回本，只剩 5 轮） |
| 变体 B：甩得多 | 400,000 | 30,000 | 10 | 0.1 | 1.25 | 37,000 | −2,500 | 0 | 值得（重建那一轮就已经便宜了，立即回本） |

算例只算缓存这一项。加上先验的重建后代价，回本轮数多出 0.1 × 写价 ÷ 读价 = 1.25 轮：默认值变成 5 轮，变体 A 变成 47 轮，变体 B 不再是立即回本而是 2 轮，三个结论都不变。

方向是稳的：**甩掉的越多、剩余轮数越长，越划算**；两个倍率的具体数字会挪动回本轮数，但不会让结论掉头。

## 三样别人做不到的

**这一节回答**：为什么这是 sage 的特色，而不是又一个谁都能加的功能？

**看得见每个 token 为什么在那里。**每一次调用模型都留下一份清单。harness-pi 的生产级架构那份文档把「生产级」定义成 headless、无人值守、跑在别人的仓库里——那种场景下最缺的一句话就是「它当时到底看到了什么」。而且这份可观测性自带一个指标：`expand` 的调用率就是打分器的漏判率，可以在线测，直接接进 run 健康度信号（口径从 harness-pi docs/13 §3.6 搬，那套信号里本来就有缓存命中率和悬空 toolCall 扫描）。

**阶段边界零代价换模型。**一方出品的 agent 结构上只能用自家模型，这件事它做不了。sage 不依赖任何把 provider 藏起来的抽象层，自己写 Anthropic Messages 与 OpenAI 兼容两类适配，类型面是本仓的——中立性的红利照样成立，而且看得见。而阶段边界那一刻缓存本来就要重建，在那里按难度、成本、数据敏感度换一个模型不多花一分钱——「切回大模型要重读一遍」这笔账，在阶段模型下根本不存在。

**子任务和后台任务不复制历史。**子 agent 不再是「从零起步」和「复制一整段前缀」的二选一：它就是换个问题、换个预算，在同一份 Log 上再编译一次；后台的只读任务——审查、eval、跨模型复看——共享同一份检索结果。这几样从 harness-pi 搬：派子任务的工具、并行跑的工作池、七个第一方工具上已经声明好的危险度元数据（只读的是 `read` / `grep` / `find` / `ls`），以及把产出回灌给父会话的通道。harness-pi 的裁决①算过：1000 条记录的会话派 8 个分支就是 8000 行纯重复——在这个模型下那笔放大不存在。

*图 4：同一份 Log 上编译出三份视图——主会话、子 agent、后台只读任务，各带自己的问题和预算。谁也不复制历史，块编号在三份视图里指的是同一份原文。预算为示意。*

## 上下文策略变成可测试的东西

**这一节回答**：怎么证明一个打分器、一条淘汰规则真的更好，而不是听起来更好？

清单加上 session-log 录下的轨迹，合起来是一份可回放的记录：换一个策略，把历史上每一轮的视图重新编译一遍，看模型的下一步动作变不变、任务成不成。策略是一个插件，回放是一个控制器，基准用 SWE-bench Verified-mini-50。

这句话有两个读者。对外它是一个说法：**上下文策略在这里可替换、可 A/B、有基准**。对内它是研发飞轮：打分器是整套方案里唯一押注的部分，风险靠回放来控，不用押上产品——这也是它排在最后一期的原因。

## 效率只认三个数

**这一节回答**：任何一期做完，拿什么说话？

| 指标 | 怎么算 | 说明什么 |
|---|---|---|
| 每个 resolved 的 token | 基准跑完，总 token 除以解决掉的题数 | 唯一一个直接对着钱的数。省了上下文却多跑几轮，这个数会把它抵回去 |
| 缓存命中率 | 前缀诊断做预测与实测对账（概念从 harness-pi 的 prefix-shape 搬），范围从「只看 system 与工具」扩到整段前缀 | 阶段冻结有没有真的成立 |
| expand 率 | 清单里 `expand` 的调用次数除以省略掉的块数 | 打分器判错的频率。高到一定程度，省下的钱会被取回原文的开销吃掉 |

三个数都能从清单和成本统计里直接算出来，不需要额外埋点。

## 建造顺序

**这一节回答**：先做哪个？每一期做完能不能单独交付？

| 期 | 做什么 | 动内核吗 | 怎么验 |
|---|---|---|---|
| M1 内核：Log + View seam | 仓库骨架、薄 provider 适配、Log、View seam + loop + hook dispatcher、直通 ViewProvider 与第一方工具、测试基础设施 | 写，这一期就是内核本身 | 干净 clone 跑通一个真实小任务；log 里每轮都有 manifest（全是 `passthrough`）；resume 之后首轮的缓存命中率不低于中断前 |
| M2 claim 预算与清单 | 申领单、预算分配、清单落盘、分块索引与确定性淘汰、留桩、`expand`、常驻区改走 claim | 不动 | 基准上的每个 resolved 的 token、expand 率 |
| M3 阶段与路由 | 阶段冻结与不等式；前缀诊断扩到整段前缀；阶段边界换模型；子 agent 走编译 | 不动 | 缓存读的预测对实测；子会话首轮成本；分支的存储量 |
| M4 打分器与回放 | 打分器接口与模型打分 adapter；离线回放控制器；三个数进 RunSummary | 不动 | 换成筛过的上下文之后，下一步动作是否一致、成功率是否下降 |

**M1 就是内核本身。**sage 不从 harness-pi 的接口出发，所以没有旧管子要留、没有兼容层要做，也不存在「把三个压缩插件迁到新接缝上」这种过渡态。换来的是：不会有 transform 的顺序铁律，不会有压缩边界的内核特判，而且从 M2 起每一期都不用再碰内核。

## 两个会咬人的细节

**这一节回答**：照着做，最容易在哪两处翻车？

**常驻片段不能塞进 system prompt。**「频繁改 system prompt」是反模式，理由就是前缀缓存要求它逐字节稳定，每轮改一次等于每轮不命中。所以条件化的常驻片段要放在**阶段头部的那条消息**里——反正换阶段本来就要重建前缀，在那一刻把它提上去不额外花钱。阶段中途才命中的片段先挂在尾部，等下一个阶段再提到头部。

**进度账本是一张钉住的申领单，不是驱动器。**目标、计划、已经定下来的决定，这几样要钉在每一轮的视图里，否则模型看到一段有空洞的历史，会把已经做完的事重做一遍——无人值守跑长任务时，这种重复没人会发现。但它的作用仅此而已：**保住任务框架，不催模型、不驱动模型**。长任务模型自己能跑完，harness 要做的只是别把它的任务框架弄丢。

### 明确不做

- **每一轮都重建视图。**那是把成本从缓存挪到打分上，账不一定划算；阶段冻结才是这套方案省钱的地方。
- **多 leaf 全树的存储契约。**harness-pi 的裁决①已经结构性否决了这个候选——没有任何消费者需要多 leaf 并行写。
- **让内核认识块的语义。**内核只拥有 Log 与 View seam；块、档位、预算、申领单全部活在插件里。这条边界一旦破了，后面每个插件都会想往内核里塞东西。
- **用「一句意图 + 路由」替掉原生的工具调用。**模型没在这种格式上训练过；延迟暴露工具加上工具搜索已经够用了。
- **任何催促、驱动、自动续跑的逻辑。**这份设计只管「这一轮发什么」，不管「要不要再来一轮」。
- **依赖 pi-ai 或任何把 provider 藏起来的抽象层。**provider 适配自写，只接 Anthropic Messages 与 OpenAI 兼容两类。

## 这份设计没核对的地方

**这一节回答**：上面哪些话是有据可查的，哪些不是。

出现过的每一个插件名、hook 名、条目类型、issue 号、裁决编号，都在 harness-pi 仓库里对得上。下面这四条不是。

1. **内核规模的对照是估计出来的。**读的是 harness-pi `session.ts` 里持有消息数组、推进持久化水位、交出缓存安全参数、组装这一轮请求这四处，没有逐行读完一千六百多行。「内核小」是基于这四处的判断，不是数出来的。
2. **两个缓存倍率未核实。**算例里的 0.1 与 1.25 是常见定价的印象值。结论的方向（甩得越多、剩余轮数越长越划算）不会因此翻转，但「4 轮回本」这个具体数字不该被当成实测值引用。
3. **走查里的数字和那张曲线都是示意。**第 37 轮、212 个块、180 块、4.2 万 token，以及那张曲线上的两条线，都是为了把机制说清楚编出来的形状，不是任何一次真实 run 的数据。真实数据要等 M3 前缀诊断扩到整段前缀之后才拿得到。
4. **最大的风险仍在打分器。**准不准，决定了 `expand` 的调用率会不会高到把省下的钱吐回去。好在它能拿录好的轨迹先做离线回放，不用押上整个产品。
