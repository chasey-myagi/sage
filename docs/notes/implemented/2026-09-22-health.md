# run 健康度

## Problem

验收要有地方读数。每个 resolved 的 token 由基准层拿总 token 去除，这一次 run 自己得先交出 token 总量、缓存命中率和 expand 率。阶段数、换模型次数、打分调用数也要能从同一次结束里读到。这些数如果另埋点，就会和 Log 里已经写下的 usage、清单分叉。输出如果带上块原文或路径，清单外流的白名单就破了。

## Decision

`runHealth(path)` 是 core 的纯函数。一次 run 结束时 `RunSummary.health` 等于它，`terminal` payload 写入同一份对象。

token 从路径上每条 assistant 消息的 `details.usage` 加总。`tokens.input` 是 `inputOther` 之和，`tokens.total` 再加 cache read、cache creation 和 output。`cacheHitRatio` 是 Σ cacheRead / Σ (cacheRead + inputOther + cacheCreation)。没有 assistant usage，或分母为 0，就是 null。`omitted` 和 `expands` 只读最后一条 manifest 的 `budget`，这两个字段已经是累计值。`expandRate` 是二者相除，`omitted` 为 0 时是 null。`epochs` 是最大 `view_epoch.epoch` 加 1，没有则是 1。`modelChanges` 是 `model_change` 的条数。`scorerCalls` 与 `scorerFallbacks` 把每条 manifest 的 `scorer.calls`、`scorer.fallback` 加起来，`true` 计 1。

`sage -p --json` 的 stdout 仍是一行 RunSummary，里面带 `health`。`sage stats <session.jsonl>` 用 `JsonlLogStore` 读该文件，打印同一份 `runHealth`，不启动 run。`health` 和 `stats` 里只有数字和 null。

## Alternatives considered

为什么 core 复刻口径，而不是 import 编译器。命中率序列今天写在 `packages/plugins` 的 `cacheHitRatio` 里，它按清单上的 `cache.measuredReadTokens / expectedReadTokens` 给出每一轮一行。core 不能认识 plugin，也不能为了这一个数把编译器拉进内核。把函数下沉到 core 会让内核开始解释清单的预测字段；把调用留在插件里，`RunSummary` 又读不到。所以 core 自己从 Log 上已经有的 usage 和 manifest 字段算，编译器继续写它的序列，两边不互相 import。

为什么命中率用 token 加权，而不是轮次平均。一轮只读了几个 token、命中率是 0，下一轮读了一大段前缀、命中率接近 1，两轮平均会把大的那一轮削成一半。钱是按 token 付的，所以分子分母都先加总再相除。插件那条序列仍是逐轮的预测对实测，留给前缀诊断；进 RunSummary 的这个数回答的是「这次 run 的输入里有多少来自缓存」。

## Consequences

不做 SWE-bench，不做仪表盘，不改编译器。子会话的 usage 仍不进父 run 的 `usage`，`runHealth` 也只看交给它的那条 path。`terminal.health` 缺省合法，出现时必须是对象，内核不读里面的字段。

`text-only` 和 `tool-roundtrip` 的 terminal 期望都带上 `health`。回放比较的是规范化之后的 payload，原来的 entry id 和时间戳保留。

## Testing

`pnpm check` 退出码 0：lint、tsc、分层、README、log manifest，以及 56 个文件 253 个测试。红灯时 `health.ts` 不存在（`Cannot find module '../../src/health.ts'`），`--json` 被当成未知参数，terminal 的非对象 `health` 不被拒绝。回放在补上 `health` 之前，`normalize(result.log)` 与录制的 terminal 不一致。
