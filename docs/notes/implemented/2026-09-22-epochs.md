# 阶段冻结、成本不等式与缓存校准

## Problem

M2 的淘汰每轮都可能改写历史中间的 tool_result。前缀一变，缓存整段作废。开新阶段又是这套设计里唯一主动花钱的决定，不能靠阈值猜。

## Decision

阶段内，第一份 manifest 的块决策原样沿用。新块才走淘汰，近期窗口只在新块里数。视图断点是 `head`、冻结前缀末尾、最后一条消息。

开新阶段看不等式：每轮节省 = (旧 − 新) × 读价，重建额外成本 = 新 × 写价 − 旧 × 读价，回本轮数向上取整。读价、写价来自目录；没有定价就用 0.1 与 1.25。上一轮 usage 的输入合计除以当时的 `budget.used` 得到 ratio，之后的 token 估算乘这个 ratio。省下的比例小于 `minSavingsRatio`（默认 0.2）不开。估算超过上下文窗口的 0.9 强制开一次，reason 是 `context-window-guard`；重开后仍超就把超出记进 `budget.overrun`，同一阶段不再为这道阀重开。

`remainingTurns = max(1, expectedTurns − 已开始的轮数)`，`expectedTurns` 默认 20。

目录换成现行型号并填上 2026-09-22 核对过的价格。`cache` 字段留给 `cacheHitRatio`，给 #17 读命中率序列。

## Alternatives considered

为什么用第一份 manifest 当冻结记录，而不是新 entry。块的档位和 reason 本来就要进清单。再加一种 entry，内核就得认识「冻结」这个插件概念，也和 L7「清单落在不透明 payload」重复。第一份清单紧跟 `view_epoch`（阶段 0 没有 `view_epoch` 时就是路径上的第一份），回放时找得到，不必再写一条只为搬运同一份决策的记录。

为什么 remainingTurns 用配置，而不是预测。不等式要的是「还打算走多少轮」，不是模型会不会提前停。预测剩下的轮数要另一次模型调用，那笔调用自己也要付前缀，而且错了会让开阶段的决定不可回放。配置的 `expectedTurns` 是调用方的预算，用 Log 上的 turn 减出来，同一份 Log 得到同一个数。

为什么 context-window-guard 是安全阀不是策略。窗口的 0.9 不是「划不划算」，是请求已经快装不下。把它写进不等式会让阈值重新决定开不开阶段，这正是设计要拿掉的锯齿。阀只强制重开一次；重开后仍超就记账，不再为同一原因连环重开，免得每轮都砸前缀。

## Consequences

阶段内前缀逐字节不动，尾部追加。换模型仍是 #13，本票 model 不变。子 agent、打分器、淘汰规则本身都不动。目录里退役的 `claude-opus-4-1` 删掉，默认型号变成 `claude-sonnet-5` 和 `gpt-5.4`。OpenAI 的 `cacheWrite` 为 0，重建没有额外写费，不等式照算。

阶段第一轮旧视图与新视图相同，除安全阀外不开新阶段，避免空会话写出 `view_epoch`。内核仍把 `messages[0]` 存进 `view_epoch.details.epochHead`；若那条消息本身就是 Log 里的历史，下一轮不再把它插到视图前面。
