# 可替换打分器

## Problem

整套方案里唯一押注的部件是「这一块该不该留全文」。它必须能换，而且换的时候不能把阶段内已经暖好的缓存前缀打掉。辅助调用如果自带一套 system 或丢掉 tools，前缀从第一个 token 就对不上，历史要按全价再付一遍。模型打分失败也不能让这一轮发不出去。

## Decision

块的档位仍先走四条确定性规则（superseded、retry、recent、预算）。打分器只接收剩下的 `kept` 工具块，而且只在 `decideEpoch().rebuild` 为 true 时调用。

`Scorer.score` 是可替换接口。默认 `ruleScorer` 对每个候选给 full，不报 usage，编译器不改 reason。`modelScorer` 由调用方注入 adapters。它把上一轮主请求的 head 和 messages 原样抄过来，末尾追加一条 user 消息（固定指令、当前问题、候选清单），tools 照带。`prevRequest` 用 `rebuildFromLog` 从上一轮的 `request_header` 和清单重建。没有上一轮请求时直接 `fallback: "no-previous-request"`，不打网络。

模型只应返回 JSON，tier 限于 none、summary、full，summary 最长 200 字符。summary 档的 tool_result 是桩行加换行加 `summary (model notes, not evidence): `。这段字符串写在清单 chunk 的 `summary` 字段上，阶段内后续轮次从这份清单读回。非法 JSON、超时（默认 20000ms）、finish error 都退回规则档，`epochDecision.reason` 追加 `;scorer:fallback:<原因>`，本轮照常发出。调用本身的 usage 记在清单 `scorer: { calls, usage, fallback }`。

recent、superseded、retry、预算这四条优先于打分器。CLI `--scorer model` 只给根编译器装上模型打分，模型用当前会话的型号。

## Alternatives considered

为什么打分只在重开时跑。阶段内的省钱来自前缀冻结，不是来自每轮重新打分。每轮都打，等于把成本从缓存挪到辅助调用上，而且打分结果一变，冻结前缀就断了。不等式已经决定这一轮值不值得重开；打分是重开之后对 kept 块的再分配，不是另一道开阶段的开关。

为什么用上一轮请求，而不是当前正在组装的视图。辅助调用要命中的是已经发给 provider、缓存已经暖过的那一条前缀。当前视图是这次编译的产物，它还没发出去，也还没进缓存。用它当头，前缀对的是一份世界上还不存在的请求。上一轮 `request_header` 加 `rebuildFromLog` 才是那次真正发出去的 head 和 messages。

为什么 summary 直接写进清单，而不是另做内容寻址。笔记是短文本，上限 200 字符，每次打分都可能不同。为它再哈希、再单开一条 entry，读回时多一次查找，省不下多少字节。清单 chunk 上的 `summary` 字段就是模型看见的那句话，`rebuildFromLog` 用它把 tool_result 还原成同一行桩加同一句笔记。

## Consequences

确定性淘汰的四条规则没有改。打分器换实现不影响 claim、路由和阶段不等式的形状。没装打分器时回放产物不变。

`rebuildFromLog` 现在会还原 summary 档，否则下一轮的打分前缀和子任务看到的父视图会对不上当时发出去的字节。离线回放（#16）和 RunSummary 里的打分用量（#17）还没做；#17 读的就是这次写下的 `manifest.scorer`。

子任务编译不重开阶段，因此不会调用打分器。根会话的 `--scorer model` 不会自动装到子编译上。
