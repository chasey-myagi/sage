# 子任务 = 同一份 Log 再编译

## Problem

子会话如果从零开始，就看不到父会话已经冻结的前缀。如果把父 Log fork 一份再跑，1000 条记录派 8 个分支就是 8000 行重复，而且块编号两边不再指同一份原文。只读子任务要能并行，又不能为了少带工具去改 head：system 和 tools schema 一变，父前缀的缓存就断了。

## Decision

子任务是换一个问题、换一份预算，在同一份 Log 上再编译一次。子会话有自己的 sessionId，第一条 entry 是 `subtask`，记下父 session、父 leaf、query、budget、readOnly。父 leaf 之前的 entry 不复制。

子视图的头与父上一次请求相同。消息从父路径上最新一份 manifest 重建（epoch 头和已冻结的桩都在里面），父块沿用该 epoch 的 `frozenDecisions`，id 仍是 `seq:N` / `seq:N#id`。子会话自己的消息是 `own:` 块，走淘汰。query 不写进历史，作为尾部申领单 `subtask-query` 接在冻结前缀之后。子编译不调用 `decideEpoch`，清单 reason 是 `subtask:no-rebuild`。

`readOnly: true` 不改工具列表。guard 否决 `isReadOnly === false` 的调用，tool_result 为 `Denied: read-only subtask`。`spawn_subtasks` 只接受全部只读的一批，用信号量并行，默认同时 4 个。纵向默认到孙会话（`maxDepth` 2），每个会话横向默认 8 个（`maxSubtasks`）。跑完即回：父 tool_result 带最后一条 assistant 文本和 `child:<sid>#<chunkId>`。`expand` 按这个 id 取回原文。子 usage 只进这次 details，不进父 RunSummary。

## Alternatives considered

为什么不 fork 复制。复制能让子请求的前缀字节与父相同，从而吃到缓存，但存储按分支放大，块编号也不再指同一份 entry。重建父请求只读父路径，前缀字节一样，存储只多出子会话自己的清单和消息。

为什么只读靠 guard 不靠换工具集。只读要保证的是不能执行写工具，不是模型看不见它们。从 head 里拿掉写工具，tools 块就和父请求不一样，冻结前缀的缓存从第一个字节起失效。guard 在执行前否决，schema 保持不变。

为什么子任务一次性。子视图要复用父的头和冻结前缀，就不能再拥有自己的阶段重开，也不能变成一条长期会话：阶段重开会换头，续聊会在共享前缀后面长出第二套历史。一次性跑完把块编号交回去，父视图用 expand 取原文。持续会话不在这次的范围内。

## Consequences

子会话的 `view.epoch` 沿用父 epoch。内核因此可能在子路径上写一条 `view_epoch`，reason 是 `epoch-advanced`，不是成本重开。清单上的 `epochDecision.rebuild` 仍是 false。

父 RunSummary 不累计子 usage。口径留给 #17。跨进程子 agent、自动并行决策、打分都不在这次。

`expand("child:<sid>#seq:N")` 顺着子会话的 `subtask` 指回父 leaf。`own:` 前缀则留在子路径上解析。

## Testing

`pnpm check` 退出码 0（lint、tsc、分层、README、log manifest、225 个测试）。前缀用 `renderLlmInput(childReq, parentLastReq)`，输出是 `system: <same>`、`tools: <same>` 和 `<last>` 加尾部申领单。只读否决、并行池重叠、深度与数量上限、块 id、`expand` 的 `child:` id、以及 CLI 一条 e2e 都在同一轮测试里。红灯时 `subtask` 是未知 kind，`ViewContext.depth` 为 undefined，`subtaskTools` 不是函数。
