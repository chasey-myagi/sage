# claim 申领单、预算分配与编译器骨架

## Problem

插件往上下文里塞文本时，没有人在总预算下算总账。提醒、协议、账本如果写进历史，又会把阶段前缀弄脏，缓存跟着失效。

## Decision

插件提交申领单，不提交文本。`contextCompiler` 收齐申领单后做一次纯分配：pinned 取最高可用档且永不降，其余先取最高档，超预算则从低优先级、当前最高档开始降一档，缺的档跳过，最低落到 `none`。`none` 不进视图。

组装时 head 仍是会话注入的那一份。历史沿用 passthrough 的投影和修复，每条历史消息在清单里是一块，tier `full`、reason `passthrough`。epoch-head 按 priority 降序渲染成一条 user 消息，放在历史前面；本 epoch 的 `view_epoch.details.epochHead` 已存在时原样沿用，提供者的新正文被忽略，reason 为 `frozen:epoch-head`。`tail` 与 `tail-if-changed` 用同一段包裹格式，作为 text block 追加到最后一条 user 消息末尾；最后一条不是 user 时另开一条。`tail-if-changed` 与路径上最近一条 manifest 的 contentHash 比较，没变 reason 为 `unchanged`，变了为 `changed`。全文只在哈希首见或变化时放进 `details.claimContent`。

内核在 `view_compiled` 之后、`request_header` 之前：若 `view.epochStart` 存在，或 `view.epoch` 大于路径上最近的 `view_epoch`（没有则视作 0），追加 `view_epoch`，`details.epochHead` 为 `messages[0]`。manifest 的 `details` 原样落盘。`budget` 可以是有限数字，或 `{ total, used, overrun }`。编译器自己不把 epoch 加一。`rebuildFromLog` 用阶段头、message entry 和按哈希找回的 claim 正文，重建当时发给适配器的 head 与 messages。

## Alternatives considered

账本走 `tail-if-changed`，不进 epoch-head。进度账本一轮里可能只改几个字。放进阶段头，一变就要重开阶段，前缀缓存整段作废。挂在尾部，没变就不写新全文，变了也只动消息末尾。

`claimContent` 按内容寻址放在 manifest 的 `details`，不新开 entry 类型。L7 把清单和 claim 历史留在不透明 details 里，内核 schema 不认识插件字段。全文只在哈希首见或变化时存，和 `request_header` 对 system / tools 的做法一样。单独一种 entry 会让内核认识 claim 正文，也会让每一轮多一条只为搬运字符串的记录。

`none` 档不留桩。降到 `none` 就是这一轮不展示。留桩句式和 `expand` 是 #10，本票不写占位符。

## Consequences

没有申领单时，视图与 passthrough 逐字节相同，清单只多一个 `budget` 对象，claims 仍为空。历史 chunk id 每次回放都会变，比较时收成 `seq:N`。场景 7 的编译器回放放在 `packages/plugins/test`，复用 core 的 `REPLAY_CASES`：core 不能 import plugin，所以不能把这个分支写进 `packages/core/test/replay/cases.ts`。

本票不做分块淘汰、留桩、第一方申领单、阶段判定和模型打分。epoch 仍由路径上已有的 `view_epoch` 决定。

## Testing

`pnpm check` 退出码 0（lint、tsc、分层、README、log manifest、138 个测试）。红灯时编译器模块不存在（`Cannot find module '../../src/compiler/budget.ts'`，以及 compiler.ts / rebuild.ts 同样的错误）；epoch 测试时期望的 `view_epoch` 不在 Log 里，kind 序列仍是 `message → request_header → manifest`。
